Executive summary: how to make and upload a GEMS submission

Written from the upload page text quoted in the project brief. The competition pages themselves were not reachable from the build sandbox, so the rules below must be re-checked on the live page before every upload.

The short version

  1. Make a single-band GeoTIFF (.tif) on the same grid as the template: CRS EPSG:32611, same shape and geotransform.
  2. Every value must be a finite number between 0 and 1. No NaN, no nodata inside the study area.
  3. Check the file with scripts/validate_submission.py. Upload only if it prints "pass": true.
  4. Give it a unique name and a short note. Upload it on the competition's New submission form.

1. What the upload form asks for

From the brief's quote of the form: File to submit accepts a single-band GeoTIFF (.tif) or a .zip containing a single GeoTIFF. It must match the submission format's CRS, shape and geotransform. The Note (optional) field is a short comment, e.g. clustering with k=25.

The brief's example form text is USER-PROVIDED. Check the live page: competition page.

2. Exact steps

Step A — get the data (on your own machine)

git clone https://github.com/buffedlizard55-lab/GEMSDOE71.git
cd GEMSDOE71
pip install -r requirements.txt
bash scripts/download_competition_data.sh   # public Dropbox links from the brief
# Then place by hand from the DrivenData data tab (login required):
#   labels.tif  training_features.tif  sample_submission.tif  1m_DEM_links.csv
# into data/

Step B — check the inputs

python scripts/prepare_data.py     # checks CRS, shape, band count; writes data/manifest.json

Step C — run the holdout first (required before any upload)

python scripts/run_holdout.py      # HOLDOUT-DTI, 95% CI, leakage canary, all-ones baseline

Do not upload unless the candidate beats the all-ones baseline on the same holdout, with a confidence interval that excludes it. Read RESEARCH §2.1 for the full gate.

Step D — write the file

python scripts/make_submission.py \
  --name h1-pu-cat-20261020 \
  --note "PU catalogue correction; HOLDOUT-DTI=<value>; not lane-checked" \
  --holdout-json runs/holdout_<timestamp>.json

The tool writes submissions/<name>.tif and a sidecar .tif.json with the sha256 and verification results. It refuses to write a file with NaN, values outside [0, 1], or a mismatched grid.

Step E — validate the file again, independently

python scripts/validate_submission.py submissions/h1-pu-cat-20261020.tif --template data/example_submission.tif

Upload only if the last line of output shows "pass": true.

Step F — upload

  1. Open the competition's New submission page and choose submissions/<name>.tif under File to submit.
  2. Paste the note into Note (optional). Keep it under 140 characters.
  3. Submit. Record the receipt: the score you see there is ORGANIZER-CONFIRMED. Anything else is not.
  4. Choose which submissions count as real entries manually, within the weekly cap shown on the submission page. This repo does not pick submissions for you.

3. The "Predicted values must be in range [0, 1]" error

Likely causeHow to checkWhat this repo does
Values above 1 (raw scores, logits, or unnormalised sums)validate_submission.py prints max and in_unit_intervalRefuses to write; never clips silently
NaN or inf inside the footprintnan_or_inf_count must be 0Refuses to write

Wrong grid (different CRS, shape or geotransform)template_*_match fields must be trueChecked against the template and re-read after writing

We have not seen the failed file, so which cause applies is UNVERIFIED. The checks above cover each cause.

4. Naming and notes

  • Name: 3–64 characters: letters, digits, . _ -. Include the hypothesis, date and a hash, e.g. h1-pu-cat-20261020-a1b2c3d4.
  • Note: at most 140 characters. Say what changed, the holdout value and its label, and whether it is lane-checked, e.g. PU catalogue correction; HOLDOUT-DTI=<value> (CI <lo>-<hi>, n_folds=<k>); not lane-checked with the numbers copied from your run (no example numbers are given here on purpose).

5. Do not upload if any of these are true

  • The file came from synthetic test data (the selftest files are not submissions).
  • The validator did not pass.
  • There is no holdout result, or it does not beat the all-ones baseline with a CI that excludes it.
  • A leakage canary flag is open for review.
  • The lane check against other registry rasters has not been run (it has not been run yet; see FLAGS F12).
